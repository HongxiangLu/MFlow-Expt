# 藏品 3D 模型生成流程规范

## 1. 背景

当前项目中的藏品模块主要用于展示 3D 模型，前端通过静态 `modelUrl` 加载 `glb/fbx` 文件完成渲染。

相关代码位置：

- `src/pages/collection/data.ts`
- `src/components/collection-3d-stage/collection-3d-stage.tsx`

这意味着当前系统已经具备“展示模型”的能力，但还不具备“用户上传图片 -> 后台调用腾讯混元 3D -> 生成模型 -> 回填到藏品”的完整生产链路。

本文目标是定义一套适合当前项目的规范化流程，后续可直接作为后端实现依据。

## 2. 目标

建立一条标准的异步任务链路：

1. 用户上传藏品图片。
2. 后台接收并校验图片。
3. 后台调用腾讯混元 3D API 提交生成任务。
4. 后台轮询任务状态。
5. 任务成功后获取 3D 模型结果。
6. 对结果模型做必要的轻量化、格式转换和持久化存储。
7. 将最终模型地址写入藏品数据。
8. 前端继续复用现有 3D 展示组件进行渲染。

## 3. 总体原则

### 3.1 前端不直连腾讯 API

前端只负责：

- 上传图片
- 查询我方任务状态
- 展示最终模型

前端不应直接调用腾讯混元 API，原因如下：

- 密钥不能暴露给前端
- 腾讯返回结果地址通常是临时地址，不能直接作为长期馆藏资源
- 任务状态、失败重试、限流控制应统一收敛在后台

### 3.2 使用异步任务流，不做同步阻塞

3D 模型生成本质上是耗时任务，不适合同步请求内完成。推荐采用：

- 上传接口：快速返回任务 ID
- 后台 worker：异步提交和轮询
- 前端：轮询我方任务状态接口

### 3.3 模型结果必须落到我方存储

腾讯返回的模型结果地址不应直接入库作为正式资源。标准做法是：

1. 下载腾讯生成结果
2. 上传到我方对象存储（如 COS）
3. 以我方永久 URL 作为最终 `modelUrl`

## 4. 推荐流程

## 4.1 流程图

```text
用户上传图片
  ->
我方后台接收文件
  ->
图片校验与预处理
  ->
上传原图/预处理图到我方 COS
  ->
调用腾讯 SubmitHunyuanTo3DProJob
  ->
记录 JobId 并返回我方 taskId
  ->
后台定时轮询 QueryHunyuanTo3DProJob
  ->
生成成功
  ->
下载腾讯返回的模型文件
  ->
必要时调用减面/格式转换
  ->
上传最终 GLB 到我方 COS
  ->
更新藏品 modelUrl
  ->
前端展示模型
```

## 4.2 详细步骤

### 步骤 1：用户上传图片

建议前端上传一张主体清晰、背景尽量简单的藏品图片。

上传要求建议如下：

- 格式：`jpg`、`jpeg`、`png`、`webp`
- 大小：建议不超过 `8MB`
- 分辨率：单边建议在 `128` 到 `5000` 像素之间
- 内容：主体完整、无遮挡、尽量纯背景或弱干扰背景

说明：

- 腾讯接口对图像尺寸和文件大小有限制
- 单图生成 3D 对图片质量较敏感，预处理质量直接影响成模效果

### 步骤 2：后台校验与预处理

后台收到图片后，执行以下检查：

- MIME 类型校验
- 文件大小校验
- 分辨率校验
- 是否存在空文件、损坏文件
- 是否包含明显非藏品主体内容

建议增加预处理：

- 自动纠正 EXIF 方向
- 裁掉多余留白
- 尽量让主体居中
- 如业务允许，可做抠图或背景弱化

预处理后的图片建议单独保存，后续优先用预处理图调用 3D 生成接口。

### 步骤 3：创建我方生成任务

后台在数据库里创建一条 3D 生成任务记录，建议初始状态为：

- `uploaded`

同时记录：

- 藏品 ID
- 原始图片地址
- 预处理图片地址
- 上传人
- 创建时间

### 步骤 4：上传图片到我方 COS

推荐做法是先把原图和预处理图上传到我方 COS，再把公网可访问的 `ImageUrl` 传给腾讯。

推荐 `ImageUrl`，不推荐默认使用 `ImageBase64`，原因如下：

- 大文件更稳定
- 便于复用
- 更适合异步任务流
- 减少接口体积

### 步骤 5：调用腾讯混元 3D 专业版生成接口

推荐使用：

- `SubmitHunyuanTo3DProJob`

推荐参数策略：

- `Model=3.1`
- `GenerateType=Normal`
- `EnablePBR=true`
- `ImageUrl=<我方 COS 图片地址>`
- `FaceCount=150000~300000`

说明：

- `3.1` 适合高质量生成
- `Normal` 适合先生成高质量模型，再根据前端需求做减面
- `EnablePBR=true` 更适合藏品材质表现
- 面数不宜过高，否则前端展示压力变大

后台提交成功后，应记录腾讯返回的：

- `JobId`
- `RequestId`

并将状态更新为：

- `submitted`

同时向前端返回：

- 我方 `taskId`
- 当前状态

### 步骤 6：后台轮询任务状态

后台 worker 或定时任务轮询：

- `QueryHunyuanTo3DProJob`

轮询频率建议：

- 每 `10~20` 秒一次

状态建议映射如下：

- 腾讯任务刚提交：`submitted`
- 腾讯处理中：`running`
- 腾讯成功返回：`generated`
- 腾讯失败：`failed`

失败时要记录：

- 错误码
- 错误消息
- 原始返回体

便于后续排查。

### 步骤 7：处理生成结果

任务成功后，腾讯会返回 3D 结果文件信息。此时后台应立即：

1. 下载腾讯结果文件
2. 判断格式是否满足前端展示要求
3. 判断模型大小和面数是否适合 Web 展示

如果模型过重，建议继续调用：

- `SubmitReduceFaceJob`
- `QueryReduceFaceJob`

即先生成高质量模型，再产出轻量展示模型。

### 步骤 8：统一落库为我方可控模型资源

最终建议统一输出 `GLB` 作为 Web 展示主格式。

原因：

- 相比 `FBX`，`GLB` 更适合前端 Web 加载
- 结构更稳定
- 便于后续统一 CDN 缓存策略

最终模型流程建议：

1. 下载腾讯生成结果
2. 如需减面，则先减面
3. 如需转换，则统一为 `GLB`
4. 上传到我方 COS
5. 生成永久访问地址

任务状态依次更新为：

- `generated`
- `optimizing`
- `stored`

### 步骤 9：发布到藏品数据

当最终模型上传完成后，更新藏品表中的：

- `model_url`
- `preview_image_url`（如有）
- `generation_status`
- `updated_at`

最终状态更新为：

- `published`

这样前端藏品页无需大改，只要继续读取 `modelUrl` 即可展示。

## 5. 推荐状态机

建议统一采用以下任务状态：

| 状态 | 含义 |
| --- | --- |
| `uploaded` | 图片已上传 |
| `validated` | 图片校验/预处理完成 |
| `submitted` | 已向腾讯提交生成任务 |
| `running` | 腾讯正在生成 |
| `generated` | 腾讯已生成完成 |
| `optimizing` | 正在做减面/转换/清洗 |
| `stored` | 最终模型已落到我方存储 |
| `published` | 已绑定藏品并可展示 |
| `failed` | 任务失败 |

## 6. 数据库设计建议

建议新增一张任务表，例如：

- `collection_model_jobs`

建议字段如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint / uuid | 我方任务 ID |
| `collection_id` | bigint / uuid | 关联藏品 ID |
| `source_image_url` | varchar | 原始图片地址 |
| `processed_image_url` | varchar | 预处理图片地址 |
| `provider` | varchar | 供应商，固定为 `tencent-hunyuan-3d` |
| `provider_job_id` | varchar | 腾讯返回的 `JobId` |
| `provider_request_id` | varchar | 腾讯返回的 `RequestId` |
| `status` | varchar | 我方任务状态 |
| `provider_status` | varchar | 腾讯原始任务状态 |
| `generate_model_version` | varchar | 如 `3.1` |
| `generate_type` | varchar | 如 `Normal` |
| `enable_pbr` | boolean | 是否启用 PBR |
| `face_count` | int | 目标面数 |
| `raw_model_url` | varchar | 腾讯结果下载后暂存的原始模型地址 |
| `final_model_url` | varchar | 最终展示模型地址 |
| `preview_image_url` | varchar | 预览图地址 |
| `error_code` | varchar | 错误码 |
| `error_message` | text | 错误说明 |
| `raw_response` | json | 腾讯原始返回 |
| `created_by` | varchar / bigint | 创建人 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

如果后续要保留多版本模型，可再扩展一张资源表：

- `collection_model_assets`

用于记录：

- 高模
- 轻量模型
- 预览图
- 原图
- 预处理图

## 7. 后端接口建议

## 7.1 创建 3D 生成任务

`POST /api/collection-model-jobs`

请求建议：

```json
{
  "collectionId": "xxx",
  "imageUrl": "https://your-cos.example.com/source/xxx.jpg"
}
```

返回建议：

```json
{
  "taskId": "job_xxx",
  "status": "submitted"
}
```

## 7.2 查询任务状态

`GET /api/collection-model-jobs/:id`

返回建议：

```json
{
  "taskId": "job_xxx",
  "status": "running",
  "progressText": "3D 模型生成中",
  "modelUrl": null,
  "errorMessage": null
}
```

成功后：

```json
{
  "taskId": "job_xxx",
  "status": "published",
  "progressText": "模型已生成",
  "modelUrl": "https://your-cos.example.com/model/xxx.glb",
  "errorMessage": null
}
```

## 7.3 绑定藏品模型

如果业务上希望“先生成、后人工确认发布”，可以增加：

`POST /api/collections/:id/publish-model`

适合馆方人工审核模型质量后再正式上架。

## 8. 推荐的后台模块拆分

建议至少拆成以下几个模块：

### 8.1 上传模块

负责：

- 文件上传
- 文件校验
- 文件落 COS

### 8.2 任务模块

负责：

- 创建任务
- 状态流转
- 任务查询

### 8.3 腾讯混元 3D 客户端模块

负责：

- 提交生成任务
- 查询生成任务
- 提交减面任务
- 查询减面任务

不要把腾讯 API 调用散落到业务代码里，应统一封装。

### 8.4 模型资源处理模块

负责：

- 下载腾讯结果
- 模型转换
- 减面流程
- 上传最终资源

## 9. 面向当前项目的落地建议

当前前端只要求有 `modelUrl` 就能展示，因此后端第一阶段可以先实现最小闭环：

1. 用户上传图片
2. 后端提交腾讯 3D 专业版任务
3. 成功后下载结果
4. 统一上传为我方 `GLB`
5. 更新藏品 `modelUrl`

这样前端几乎不用改动。

后续增强可以分阶段推进：

### 第一阶段

- 单图上传
- 专业版 `3.1`
- 开启 `PBR`
- 最终只产一个 Web 展示模型

### 第二阶段

- 支持多视图上传
- 增强预处理能力
- 增加人工审核发布

### 第三阶段

- 一次生成两份资源
- 高质量归档模型
- 轻量 Web 展示模型

## 10. 风险点与规避建议

### 10.1 临时 URL 失效

风险：

- 腾讯返回结果链接不是长期资源

规避：

- 成功后立刻下载并转存到我方 COS

### 10.2 前端模型过大导致卡顿

风险：

- 高质量模型直接用于 Web 展示会影响性能

规避：

- 生成后增加减面流程
- Web 端统一优先使用轻量 `GLB`

### 10.3 单图效果不稳定

风险：

- 输入图片质量差时，3D 结果可能不稳定

规避：

- 提高上传规范
- 增加预处理
- 后续支持多视角图片

### 10.4 同步接口超时

风险：

- 3D 生成耗时长，同步等待会导致请求超时

规避：

- 必须采用异步任务流

### 10.5 外部 API 限流或失败

风险：

- 腾讯接口并发、积分、网络异常都会影响任务成功率

规避：

- 增加重试和告警
- 记录完整错误码和原始响应
- 做并发队列控制

## 11. 推荐结论

对当前项目，最合理的规范化流程是：

1. 前端上传图片给我方后台。
2. 后台校验并预处理图片。
3. 后台将图片存入我方 COS。
4. 后台调用腾讯 `SubmitHunyuanTo3DProJob` 提交任务。
5. 后台定时调用 `QueryHunyuanTo3DProJob` 轮询状态。
6. 成功后下载模型结果。
7. 必要时执行减面或格式转换。
8. 将最终 `GLB` 上传到我方 COS。
9. 更新藏品 `modelUrl`。
10. 前端复用现有 3D 组件完成展示。

该方案的优点：

- 与当前项目现状兼容
- 前端改造最小
- 后台流程清晰
- 便于后续扩展审核、减面、多视图输入、模型归档
