# 博物馆 3D 模型工作流程设想

## 一、 前置条件

### 1. 数据库
存有大量的数据（`id`、`name`、`url`、`type`、`status`）。
- `id`：主键
- `name`：名字
- `url`：模型存储路径
- `type`：种类（例如青铜器、画等）
- `status`：状态（展示、不展示等）

> **注**：后续可能还需要细分，例如文物 ID、文物信息、所在博物馆、所在展览等细节。

### 2. 后台管理系统
用于管理当前博物馆/数据库所存在的展品，调整数据、状态等。

---

## 二、 工作流程

1. 工作人员登录后台管理系统。
2. 进入文物管理页面。
3. 通过分类迅速定位还没有 3D 模型/信息缺失的物品，或新增物品。
4. 工作人员上传主图（如缺失），并上传要生成 3D 模型的参照图（调用腾讯混元 3D API）。
   > *混元 3D 调用流程，参考 `3D.md`。*
5. 生成成功后，文物/模型的状态变为**待审查**。
   > *设想：新增一个管理模块，用于工作人员快速审查模型。*
6. 审查操作提供两个按钮：
   - **确定**：调用后台接口，将文物信息与模型相绑定（数据库 URL 指向）。
   - **不确定**：弹出弹窗，重新上传图片/旧有图片再次生成（类似抽奖机制）。

---

## 三、 现存问题与设想解决

### 问题 1：每次都从 COS 拉取，下行流量消耗太大（成本问题）
- **设想解决**：将模型存储在本地电脑，在部署电脑上增加 TB 级硬盘，指向本地存储。

### 问题 2：3D 模型太大，前端卡死等问题
- **设想解决**：参考下文的 模型优化与压缩 及 前端进阶优化指南。

### 问题 3：腾讯混元 3D 生成的模型塑料感、陶泥感太强烈，金属感低
- **设想解决**：是否可以根据文物不同的种类，通过 Three.js 提前预设 n 套（青铜、纸、泥土等）材质规范来动态修改。

---

## 四、 技术栈

- **后端**：Python + FastAPI
- **缓存/消息队列**：Redis
- **异步任务**：Celery

## 五、 模型优化与压缩

### 1. Draco 几何压缩
这是 Google 开源的 3D 数据压缩算法。通常一个 50MB 的高精度网格模型，经过 Draco 压缩后可以缩小到 5-10MB 左右，而肉眼几乎看不出多边形的损失。前端加载时会调用 WebAssembly 进行极速解压。

### 2. KTX2 / Basis Universal 纹理压缩
在 100MB 的模型中，往往有 80MB 都是高清贴图。传统的 JPG/PNG 在前端加载后，必须解压成巨大的位图格式送给 GPU，极吃内存。将贴图转为 KTX2 格式后，不仅文件体积显著减小，更重要的是它可以保持压缩状态直接发送给显卡（GPU）渲染，显存占用量能降低 5 倍以上，极大减少前端页面崩溃的概率。

### 3. LOD（多细节层次）
把一个模型输出三个版本：1MB 的低模、10MB 的中模、100MB 的高模。前端先花 1 秒钟加载并展示低模，让屏幕不留白，然后在后台悄悄加载高模，加载完毕后瞬间替换，实现无缝过渡。

## 六、 前端进阶优化指南

### 场景一：优雅地加载大型模型并实现带有真实百分比的加载进度条

如何在 React 结合 Three.js (或 React Three Fiber) 的项目中实现？

1. **创建进度条组件 (Loader)**：
   在 R3F 中，Three.js 的画布环境和 React 的 DOM 环境是隔离的。为了在 3D 画布上方显示一个常规的 HTML 进度条，我们需要使用 Drei 提供的 `<Html>` 组件，配合 `useProgress` Hook。
2. **创建模型加载组件**：
   对于 20-100MB 级别的文件，强烈建议使用配置了 Draco 解码器的 `useGLTF`。
3. **在 Canvas 中组合 (Suspense)**：
   最后，在主入口文件中使用 React 的 `<Suspense>` 将它们组合起来。当 `RelicModel` 正在下载和解析数据时，React 会自动渲染 fallback 中传入的 `RelicLoader`。

**进阶优化建议：**
- **多个模型并发加载**：如果你在一个场景里放了多个独立的大型资产，`useProgress` 会自动计算所有被挂起资源的总体进度，你不需要为每个模型单独写进度条逻辑。
- **平滑过渡（Fade-in）**：当 100MB 的模型突然加载完成时，进度条瞬间消失，模型“砰”地一下出现，视觉冲击有些突兀。你可以使用 Drei 的 `<Suspense fallback={...}>` 配合简单的 CSS 动画，或者使用 active 状态做一个渐隐动画，让进度条慢慢消失，同时利用 Three.js 的材质 opacity 做淡入效果。
- **缓存与二次加载**：`useGLTF` 默认集成了缓存。如果用户刷新页面或重新进入组件，只要浏览器缓存没清，模型会瞬间从内存中读取，进度条可能只会闪过甚至不出现。

### 场景二：解决模型解析阻塞与卡顿问题

虽然加了进度条，但在模型下载完成并实例化的那一瞬间（主线程解析时），页面和加载动画会出现明显的卡顿。当进度条走到 100% 的那一瞬间，网络下载和 Draco 的 Web Worker 解码其实已经完成了。导致页面“冻结”甚至动画卡顿的元凶，是主线程的同步阻塞，主要由以下两个步骤引起：

- **纹理解码与 GPU 上传**：浏览器需要在主线程把 JPG/PNG 贴图解压成巨大的位图（Bitmap），然后一口气推送到 GPU 显存中。对于高精度的文物或艺术品模型，几十兆的贴图解压耗时极长。
- **着色器编译（Shader Compilation）**：Three.js 采用懒加载策略，只有在模型第一帧即将渲染到屏幕上时，才会去编译对应的材质着色器（GLSL）。这是一个纯同步过程，会把主线程死死卡住。

**彻底解决这种“最后一公里”卡顿的 4 个对策：**

#### 1. 终极解法：使用 KTX2 (Basis) 纹理格式
如果你的 3D 模型是高精度的文物扫描件，往往包含了法线贴图、颜色贴图等大量 4K 甚至 8K 纹理。传统的 JPG/PNG 是致命的。
KTX2 格式的魔力在于：它不需要 CPU 在主线程进行解压，而是保持压缩状态直接传给 GPU，由显卡硬件直接解码渲染。这不仅将解析速度提升了数倍，还能将显存占用降低 5-8 倍，彻底消除纹理上传导致的卡顿。

*如何在 R3F 中使用 KTX2：*
你需要先用工具（如开源的 gltf-transform 或网页版 glTF-Compressor）将模型贴图转换为 KTX2 格式。然后在加载时注入 `KTX2Loader`：

```jsx
import { useGLTF } from '@react-three/drei';
import { KTX2Loader } from 'three-stdlib';
import { useThree } from '@react-three/fiber';

export function RelicModel({ url }) {
  const { gl } = useThree();
  
  const { scene } = useGLTF(url, true, true, (loader) => {
    // 注入 KTX2Loader 并绑定当前的 WebGL 上下文
    const ktx2Loader = new KTX2Loader();
    ktx2Loader.setTranscoderPath('/basis/'); // 需要把 basis 转码器放到 public 目录
    ktx2Loader.detectSupport(gl);
    loader.setKTX2Loader(ktx2Loader);
  });

  return <primitive object={scene} />;
}
```

#### 2. 预编译着色器（Pre-compile Shaders）
为了防止模型挂载后第一帧的严重掉帧，我们可以在后台提前强行把着色器编译好。`@react-three/drei` 提供了一个非常方便的 `<Preload>` 组件，它会在一个看不见的离屏摄像机中预渲染一次模型，消化掉编译的卡顿，然后再把画面切给用户。

*把它直接加在场景中：*

```jsx
import { Preload } from '@react-three/drei';

export default function MuseumDisplay() {
  return (
    <Canvas>
      <Suspense fallback={<RelicLoader />}>
        <RelicModel url="/models/high-res-artifact.glb" />
        
        {/* all=true 表示预编译场景中的所有材质和几何体 */}
        <Preload all />
      </Suspense>
    </Canvas>
  );
}
```

#### 3. 利用 React 18 的并发特性 (useTransition)
如果你的项目使用的是 React 18，可以通过 `startTransition` 将状态更新（比如“加载完毕，隐藏进度条，显示模型”这个动作）标记为非阻塞的后台任务。
这样即使 Three.js 在构建场景树时占用了一点主线程时间，React 也会优先保证 DOM 层面的 UI 动画（进度条和转场特效）平滑运行，而不是死锁在一起。

```jsx
import { useState, useTransition, Suspense } from 'react';

// 在父组件中手动控制挂载时机
export function SceneWrapper() {
  const [isPending, startTransition] = useTransition();
  const [showModel, setShowModel] = useState(false);

  // 当用户点击或进度条满足条件时，平滑过渡
  const handleLoad = () => {
    startTransition(() => {
      setShowModel(true);
    });
  };

  return (
    <>
      {isPending && <div className="spinner">正在将文物数据推送到 GPU...</div>}
      <Canvas>
        {showModel && (
          <Suspense fallback={null}>
            <RelicModel url="..." />
          </Suspense>
        )}
      </Canvas>
    </>
  );
}
```

#### 4. 优化包围盒计算（Bounding Box 计算延迟）
除了纹理和材质，如果文物模型有几百万个顶点，Three.js 默认在主线程遍历这些顶点来计算初始包围盒（用于视锥体裁剪判定）也会产生几百毫秒的卡顿。

*对策：* 确保在 Blender 等建模软件导出 GLTF 时，勾选了**包含边界框 (Include Bounding Box)** 的选项。这样 Three.js 在解析时就可以直接读取 JSON 里写好的边界数据，而不需要去遍历二进制网格顶点，能省下大量的 CPU 开销。
